# 防护优化方案 v0.4 - 动态批次审查

基于测试报告分析，针对审查阶段耗时过长的问题进行优化。

---

## 一、问题分析

### 1.1 性能瓶颈

原始方案中，`quick_review` 方法每次只审查一个文档：

```
100 条样本 × 4 秒/次 = 400 秒
```

问题根因：
- 每次调用 LLM 都有网络延迟 + 处理时间
- 未利用大模型的长上下文窗口能力
- 单线程顺序处理

### 1.2 API 能力

DeepSeek API 支持：
- **128K 上下文窗口**
- 单次请求可处理大量文本
- 支持批量结构化输出

## 二、配置参数

所有参数在 `config.py` 中配置，用户可自行调整：

### 2.1 上下文窗口配置

```python
llm_context_window: int = 128000    # LLM 上下文窗口大小（tokens）
```

根据 API 文档设置，DeepSeek 支持 128K。

### 2.2 文档处理配置

```python
review_doc_max_length: int = 800    # 每个文档最大字符数（超出截断）
review_doc_chunk_size: int = 500    # 文档分割块大小（字符数）
review_doc_chunk_overlap: int = 50  # 文档分割块重叠（字符数）
```

### 2.3 Token 估算配置

```python
review_chars_per_token: float = 2.0     # 每个 token 约等于多少字符
review_system_prompt_tokens: int = 600  # 系统提示词 token 数
review_user_prompt_overhead: int = 200  # 用户提示词固定开销
review_output_per_doc_tokens: int = 80  # 每个文档输出 token 数
review_safety_margin: float = 0.9       # 安全边际系数（使用 90% 的窗口）
```

### 2.4 批量处理配置

```python
review_min_batch_size: int = 10     # 最小批次大小
review_max_batch_size: int = 100    # 最大批次大小
review_max_workers: int = 4         # 并行处理线程数
review_dynamic_batch: bool = True   # 是否启用动态批次计算
```

## 三、动态批次计算

### 3.1 计算公式

```
可用 tokens = (context_window × safety_margin) - system_prompt - user_prompt_overhead
每文档输入 tokens = doc_length ÷ chars_per_token
每文档输出 tokens = output_per_doc_tokens
最大文档数 = 可用 tokens ÷ (每文档输入 + 每文档输出)
```

### 3.2 计算示例

128K 上下文窗口，800 字符文档：

```
可用 tokens = (128000 × 0.9) - 600 - 200 = 114,400
每文档输入 = 800 ÷ 2.0 = 400 tokens
每文档输出 = 80 tokens
最大文档数 = 114,400 ÷ 480 = 238 → 限制为 100
```

### 3.3 使用方法

```python
from poisonedrag.config import get_config

config = get_config()

# 查看配置
print(f"上下文窗口: {config.llm_context_window:,} tokens")
print(f"文档最大长度: {config.review_doc_max_length} 字符")

# 计算批次大小
batch_size = config.calculate_max_batch_size(verbose=True)

# 获取详细信息
info = config.get_review_batch_info()
```

## 四、优化效果

### 4.1 性能对比

| 指标 | v0.3 固定批次 | v0.4 动态批次 | 变化 |
|------|-------------|--------------|------|
| 批次大小 | 30 | **100** | 3.3x |
| API 调用 | ~4次 | **1次** | 4x |
| 总耗时 | 53s | 88s | +35s |
| 拦截率 | 95% | **100%** | +5% |

### 4.2 为什么耗时增加但更优？

- 单次 API 调用时间变长（处理更多文档）
- 但 API 调用次数大幅减少（网络开销降低）
- 拦截率提升到 100%
- 更好地利用长上下文窗口

## 五、调优建议

### 5.1 不同场景的配置

**场景 1：追求最高性能**
```python
llm_context_window = 128000
review_doc_max_length = 600    # 减小文档长度
review_safety_margin = 0.85    # 降低安全边际
# 预期：每批 150+ 文档
```

**场景 2：追求最高准确性**
```python
review_doc_max_length = 1200   # 保留更多上下文
review_safety_margin = 0.95    # 更高安全边际
review_min_batch_size = 20     # 确保批次不会太小
```

**场景 3：低配置 API（32K 窗口）**
```python
llm_context_window = 32000
review_doc_max_length = 500
review_max_batch_size = 50
```

## 六、总结

本次优化实现了：

1. **动态批次计算**：根据上下文窗口自动计算最优批次大小
2. **配置可调**：所有参数在 config.py 中可由用户自定义
3. **100% 拦截率**：充分利用长上下文窗口提升检测效果
