# PoisonedRAG 防护优化过程

本文档记录 PoisonedRAG 项目开发过程中遇到的主要难点和解决方案。

---

## 版本演进

| 版本 | 主要优化 | 效果 |
|------|---------|------|
| v0.1 | 基础三阶段防护架构 | 搭建框架 |
| v0.2 | 投毒样本扩展至 100 条 | 覆盖更多攻击类型 |
| v0.3 | 规则引擎预筛选 | 减少无效 LLM 调用 |
| v0.4 | 动态批次计算 + 批量审查 | 速度提升 4.5 倍 |

## 难点一：LLM 审查速度慢

### 问题描述

初期版本对每条文档单独调用 LLM 进行安全审查，100 条样本需要逐条处理，总耗时超过 400 秒，平均每条 4 秒以上。这种方案在实际生产环境中完全不可接受。

### 问题分析

- **API 调用开销**：每次调用都有网络延迟、请求解析等固定开销
- **上下文浪费**：每次调用都重复传输相同的系统提示词
- **并发限制**：API 有速率限制，无法通过并发大幅提升速度

### 解决方案：批量审查

利用 DeepSeek 模型 128K tokens 的长上下文窗口，将多个文档合并在一次请求中审查。

**关键设计**：
- 动态计算批次大小：根据当前上下文占用情况，自动计算还能容纳多少文档
- 智能分割：确保每个批次不超过模型上下文限制
- 结果解析：让 LLM 返回 JSON 数组，批量解析审查结果

**优化效果**：
- 总耗时从 400+ 秒降至 89 秒
- 平均每条从 4+ 秒降至 0.89 秒
- 速度提升约 4.5 倍

## 难点二：拦截率不达标

### 问题描述

早期测试中，部分隐蔽性较高的投毒样本未能被 LLM 正确识别，拦截率一度徘徊在 85% 左右。

### 问题分析

- **Prompt 设计不足**：审查指令不够明确，LLM 容易遗漏风险点
- **类型覆盖不全**：部分攻击类型（如依赖投毒）未被明确告知 LLM
- **风险阈值设置不当**：阈值过高导致部分高风险文档被放行

### 解决方案：优化审查 Prompt

重新设计审查提示词，明确列出所有需要检测的攻击类型，并给出具体的判断标准。

**优化要点**：
- 明确列出 6 大类攻击类型的特征
- 要求 LLM 对每个类型逐一检查
- 提供风险评分的量化标准（0-1 分）
- 强调代码审查的安全性要求

**优化效果**：
- 拦截率从 85% 提升至 100%
- 对隐蔽性样本（high stealth）的识别能力显著增强

## 难点三：正常文档误判

### 问题描述

在提高拦截率的同时，出现了正常文档被误判为投毒的情况，影响了系统的可用性。

### 问题分析

- **过度敏感**：部分正常的技术文档包含"危险"关键词，但实际是安全的教学内容
- **上下文缺失**：短文本缺乏足够上下文，LLM 难以判断真实意图
- **Prompt 过于激进**：要求 LLM 宁可错杀不可放过，导致误报率上升

### 解决方案：平衡审查策略

调整审查策略，在安全性和可用性之间寻找平衡点。

**优化要点**：
- 区分"描述性内容"和"执行性内容"：教学文章中描述漏洞原理是安全的
- 引入风险等级判断：高风险（明确恶意）vs 中风险（需要人工审核）vs 低风险（正常）
- 设置合理的阈值：低于阈值自动通过，高于阈值进入人工审核队列
- 保留人工审核入口：可疑文档不直接拒绝，而是进入待审核队列

**优化效果**：
- 误报率控制在合理范围内
- 正常技术文档能够顺利入库
- 可疑文档进入人工审核流程

## 难点四：配置参数分散

### 问题描述

项目初期各模块的配置参数分散在多个文件中，修改配置需要改动多处代码，维护困难。

### 问题分析

- **单例模式缺失**：每次获取配置都创建新实例，参数不一致
- **硬编码问题**：批次大小、阈值等参数直接写在代码中
- **环境适配困难**：开发/测试/生产环境无法灵活切换

### 解决方案：统一配置管理

创建统一的 Config 类，集中管理所有配置参数。

**设计要点**：
- 单例模式：全局共享同一个配置实例
- 预设模式：提供 strict/standard/performance/development/disabled 五种预设
- 环境变量支持：API 密钥等敏感信息从环境变量读取
- 动态计算：批次大小等参数根据模型能力动态计算

**配置项分类**：
- **模型配置**：API 密钥、模型名称、上下文窗口大小
- **防护配置**：三阶段开关、风险阈值
- **审查配置**：文档分块大小、批次大小计算参数
- **路径配置**：向量库路径、数据文件路径

## 难点五：前端功能冗余

### 问题描述

初版前端包含了投毒测试、防护统计等开发调试功能，对普通用户来说过于复杂，且投毒测试已通过 pytest 实现。

### 问题分析

- **功能堆砌**：开发过程中不断添加调试功能，未及时清理
- **用户定位不清**：未区分普通用户和开发者的需求
- **重复实现**：前端投毒测试与 pytest 测试重复

### 解决方案：精简前端功能

重新定位前端目标：为普通用户提供简洁的对话和知识库管理界面。

**保留功能**：
- 智能对话：RAG 检索增强生成
- 防护模式：三阶段防护开关和预设模式
- 知识库管理：文档上传、审查、入库

**移除功能**：
- 投毒测试：已通过 pytest 完整实现
- 防护统计：集成到 pytest 测试报告中
- 调试面板：开发调试用，不面向用户

**优化效果**：
- 界面简洁，用户上手更容易
- 功能聚焦，核心流程清晰
- 与测试框架分工明确

## 难点六：测试报告可读性差

### 问题描述

pytest 默认输出缺乏统计汇总，无法直观了解防护效果，需要手动计算拦截率等指标。

### 问题分析

- **输出碎片化**：每个测试用例单独输出，缺乏整体视图
- **缺少统计**：没有汇总拦截数、成功率等关键指标
- **难以追溯**：测试失败时难以定位具体样本

### 解决方案：自定义测试报告

实现专门的测试指标收集和报告生成模块。

**报告内容**：
- 投毒拦截率：总样本数、成功拦截数、拦截率百分比
- 阶段分布：入库阶段、检索阶段、生成阶段各拦截多少
- 性能统计：总耗时、平均每条耗时
- 召回率测试：正常文档的入库成功率

**实现方式**：
- 使用 pytest fixture 收集测试数据
- 测试结束后统一输出汇总报告
- 支持 JSON 格式保存测试结果

## 经验总结

### 1. 性能优化思路

- **减少调用次数**：利用长上下文批量处理，比优化单次调用更有效
- **动态计算**：根据实际资源动态调整参数，比固定参数更鲁棒
- **分层防护**：规则引擎快速过滤 + LLM 精细审查，平衡速度和效果

### 2. 安全与可用性的平衡

- **阈值设计**：提供可调节的风险阈值，适应不同安全需求
- **人工审核**：可疑内容不直接拒绝，保留人工介入通道
- **渐进式防护**：预设模式满足常见场景，独立开关支持定制

### 3. 架构设计原则

- **配置集中**：所有可调参数统一管理，方便维护
- **职责分离**：前端面向用户，测试框架验证功能
- **文档同步**：代码变更及时更新文档，保持一致性

---

## 后续优化方向

1. **多模型支持**：支持更多 LLM 后端，降低对单一 API 的依赖
2. **增量审查**：文档更新时只审查变更部分，提升效率
3. **实时监控**：接入日志系统，实时监控拦截情况
4. **持续学习**：收集误判案例，优化审查 Prompt
