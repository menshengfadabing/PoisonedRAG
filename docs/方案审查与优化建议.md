# 三阶段防护方案审查与优化建议

> 生成日期：2026-04-11
> 审查范围：入库审查（Stage 1）、检索过滤（Stage 2）、生成校验（Stage 3）

---

## 一、总体评估

| 阶段 | 状态 | 评分 | 主要问题 |
|------|------|------|----------|
| **Stage 1: 入库审查** | ✅ 基本可用 | ⭐⭐⭐⭐ (4/5) | 提示词过于简略，缺少样例和领域覆盖 |
| **Stage 2: 检索过滤** | ⚠️ 有缺陷 | ⭐⭐⭐ (3/5) | 语义异常检测阈值过严，可信来源列表过窄 |
| **Stage 3: 生成校验** | ✅ 基本可用 | ⭐⭐⭐⭐ (4/5) | 事实一致性依赖 LLM，无权威知识库对比 |

---

## 二、各阶段详细审查

### Stage 1: 入库审查（`BATCH_REVIEW_PROMPT`）

**当前提示词（~260 字符）：**
```
你是文档安全审查员。批量审查文档，只返回 JSON。
返回格式: {"results": [{"id": 1, "status": "p"}]}
status 只有三个值: p(安全), r(需人工复核), f(高风险)
检查重点: 可疑包名、硬编码凭证、危险命令、钓鱼欺诈/误导建议/依赖投毒/错误事实注入
```

**问题清单：**

1. **提示词过于简略** — 仅 260 字符，缺乏：
   - 各 risk type 的详细判定标准
   - 示例（few-shot examples），LLM 缺乏参照
   - 隐蔽攻击（stealth attack）的识别指导
   - 跨领域安全知识的覆盖

2. **领域覆盖严重偏向编程/IT**：
   - 规则检查器 `RuleChecker.OFFICIAL_PACKAGES` 包含 90+ 个 Python 相关包名
   - 但无任何金融、医疗、法律、教育、学术领域的关键词
   - 导致非编程领域的投毒（如伪造医疗建议、金融诈骗）可能漏检

3. **缺少样例输入** — LLM 没有见过 "什么是好的 p/r/f 判定" 的示例，完全靠零样本推理

4. **敏感关键词列表偏窄** — `sensitive_keywords` 仅 24 个关键词，全部围绕编程安全

5. **规则引擎覆盖面有限** — `SENSITIVE_KEYWORDS` 仅 13 个，主要为代码执行相关函数

### Stage 2: 检索过滤（`ContentFilter`）

**问题清单：**

1. **语义异常检测阈值过严** — 使用恶意模式库做余弦相似度检测，阈值 `0.3`，导致大量正常文档被误判为异常
2. **可信来源列表过窄** — `trusted_sources` 仅 8 个，且全部为 Python 相关
3. **来源可信度检查对用户上传文档不公平** — 上传的 `.docx`/`.pdf` 文件名（如 "论文翻译1.docx"）不在白名单中，会被扣分
4. **已修复** — `reviewed=True` 的文档现在只进行轻量级关键词检查

### Stage 3: 生成校验（`ResponseValidator`）

**问题清单：**

1. **事实一致性检查依赖 LLM 自身判断** — 让 LLM 判断自己的输出是否与检索文档一致，存在自我验证偏差
2. **无权威知识库对比** — 没有接入外部权威数据源（如 Wikipedia、官方文档）进行事实核查
3. **安全规则检查覆盖面有限** — 与 Stage 2 共用同一套关键词

## 三、优化建议（按优先级排序）

### 优先级 1: 升级入库审查提示词（高影响，低成本）

**建议方案：**
- 增加 few-shot 示例（每个评级 2-3 个示例）
- 扩展风险类型判定标准，覆盖金融、医疗、法律、教育等领域
- 增加隐蔽攻击识别指导（如：真假混杂内容、渐进式引导）
- 保持 JSON 输出格式不变，不增加 token 开销

### 优先级 2: 扩展规则检查器覆盖领域（高影响，中成本）

**建议方案：**
- 新增金融领域关键词（投资、理财、收益率、保本等）
- 新增医疗领域关键词（处方、用药、诊断、治疗方案等）
- 新增法律领域关键词（诉讼、判决、律师费等）
- 新增教育/学术领域关键词（论文代写、保录、内部渠道等）

### 优先级 3: 升级模拟投毒语料（中影响，低成本）

**建议方案：**
- 新增金融诈骗类投毒样本
- 新增医疗误导类投毒样本
- 新增法律欺诈类投毒样本
- 新增教育/学术不端类投毒样本
- 新增日常生活安全类投毒样本

### 优先级 4: 优化检索过滤（中影响，中成本）

**建议方案：**
- 放宽语义异常检测阈值或调整检测逻辑
- 扩大可信来源列表
- 对已审查文档增加 `reviewed=True` 标记（已修复）

## 四、投毒语料覆盖分析

**当前覆盖领域统计：**
| 领域 | 样本数 | 占比 |
|------|--------|------|
| Python 编程 | ~60 | 60% |
| JavaScript/Node.js | ~4 | 4% |
| 数据科学/ML | ~8 | 8% |
| 容器/云服务 | ~16 | 16% |
| 安全/密码学 | ~12 | 12% |
| **金融** | 0 | 0% |
| **医疗** | 0 | 0% |
| **法律** | 0 | 0% |
| **教育** | 0 | 0% |
| **日常生活** | 0 | 0% |

**建议新增领域及样本类型：**

1. **金融诈骗类** — 伪造投资建议、虚假理财产品、伪造税务指南
2. **医疗误导类** — 伪造用药指南、虚假诊断建议、替代疗法误导
3. **法律欺诈类** — 伪造法律条文、虚假维权指南、伪造合同模板
4. **教育/学术不端类** — 论文代写服务、虚假招生信息、伪造学术规范
5. **日常生活安全类** — 伪造食品安全指南、伪造应急处理建议

---

## 五、总结

当前三阶段防护在**编程领域**表现良好，但在**跨领域安全防护**方面存在明显短板。最关键的优化点是：

1. **升级 LLM 审查提示词** — 增加跨领域安全判定标准和 few-shot 示例
2. **扩展规则检查器** — 增加金融、医疗、法律等领域的敏感关键词
3. **丰富投毒语料** — 覆盖更多领域，确保测试全面性

这些优化的核心思路是：让防护系统从"编程领域专用"升级为"通用安全防护"。
