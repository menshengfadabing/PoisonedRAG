# PoisonedRAG 防毒方案审查与优化建议

> 审查日期：2026-04-10
> 审查范围：全系统安全架构、代码质量、测试覆盖、生产就绪度

---

## 一、总体评价

### 1.1 架构评分：**B+（良好）**

PoisonedRAG 采用**纵深防御（Defense-in-Depth）**三阶段架构，设计思路正确。核心亮点：

| 优势 | 说明 |
|------|------|
| ✅ 分层防御 | 入库审查 → 检索过滤 → 生成校验，独立可开关 |
| ✅ LLM 批量审查 | 利用长上下文窗口，一次 API 调用审查多文档，效率提升 4.5x |
| ✅ 规则引擎预筛 | RuleChecker 快速拦截已知危险模式，减少 LLM 调用 |
| ✅ 丰富的投毒样本 | 100+ 条覆盖 20+ 分类、3 个隐蔽等级的测试语料 |
| ✅ 配置化设计 | 防护模式预设 + 独立开关，灵活适配不同场景 |

### 1.2 核心风险等级分布

| 风险等级 | 数量 | 优先级 |
|---------|------|--------|
| 🔴 **严重** | 5 | 必须修复 |
| 🟡 **高** | 7 | 建议修复 |
| 🟢 **中/低** | 8 | 后续优化 |

## 二、严重问题（必须修复）

### 🔴 S1：生成校验仅"建议"不"拦截"

**位置**：`rag/generator.py` → `_build_graph()` → `validate_node`

**问题**：LangGraph 工作流是线性的 `retrieve → generate → validate → END`，无论校验结果如何，响应**始终返回给调用方**。`is_safe=False` 只是一个标记，实际不阻止不安全内容输出。

**影响**：即使生成校验检测到危险内容，用户仍然看到完整的有害响应。

**修复建议**：
```python
# 方案A：条件边路由（推荐）
def should_block(state: RAGState) -> str:
    if not state["is_safe"]:
        return "block"  # 走安全兜底回复
    return "end"

workflow.add_conditional_edges("validate", should_block, {
    "block": "safe_fallback",
    "end": END,
})
```

```python
# 方案B：在 validate_node 中替换不安全响应
if not validation_result.is_safe:
    return {
        "response": "⚠️ 检测到潜在安全风险，已拦截该响应。",
        "is_safe": False,
        "warnings": validation_result.warnings,
    }
```

---

### 🔴 S2：流式输出完全绕过安全校验

**位置**：`rag/generator.py` → `stream()`

**问题**：`stream()` 方法直接调用 LLM 流式输出，**完全跳过 retrieve_node 和 validate_node**。启用流式输出的前端即可绕过所有生成阶段防护。

**影响**：攻击者可通过要求流式输出规避所有生成校验。

**修复建议**：
- 方案A：流式输出前先通过 retrieve + validate 非流式检查
- 方案B：流式输出中实时拦截（复杂度高）
- 方案C：明确文档化 `stream()` 为"无防护模式"，默认禁用

---

### 🔴 S3：可信来源绝对绕过机制

**位置**：`security/filter.py` → `filter_document()`

**问题**：
```python
if self._check_source_trust(source):
    return FilterResult(is_safe=True, ...)  # 完全跳过所有内容检查
```
只要 `source` 匹配 `trusted_sources` 中的任意子串，**所有内容检查直接跳过**。

**影响**：若可信来源的文件被篡改或混入恶意内容，完全无法检测。

**修复建议**：
- 可信来源仅降低风险阈值，不跳过检查
- 或至少保留关键字检查，仅跳过语义异常检测

---

### 🔴 S4：入库阶段 KnowledgeBase 无内建安全检查

**位置**：`data/knowledge_base.py`

**问题**：`KnowledgeBase.add_document()` / `index_to_vectorstore()` 直接写入向量库，**不触发任何安全审查**。DocumentReviewer 仅在应用层（`app.py`）调用，不内建于 KnowledgeBase。

**影响**：任何直接调用 KnowledgeBase API 的代码均可绕过安全审查写入毒化文档。

**修复建议**：
- 在 KnowledgeBase 中添加可选的 `reviewer` 依赖
- 或提供 `SecureKnowledgeBase` 子类，强制审查后入库

---

### 🔴 S5：恶意模式检测仅支持中文

**位置**：`security/filter.py` → `MALICIOUS_PATTERNS`（8 条中文）
同时 `security/validator.py` → `UNSAFE_KEYWORDS`（6 条中文）

**问题**：知识库中包含大量英文技术文档（Python/Django/FastAPI），但安全过滤的恶意模式和关键字**全部为中文**，对英文投毒完全无效。

**影响**：英文恶意指令（如 `"ignore previous instructions"`, `"execute this code"`, `"your password is"`）无法被检测。

**修复建议**：补充英文恶意模式和关键字，至少覆盖 OWASP Top 10 注入模式的英文变体。

## 三、高风险问题（建议修复）

### 🟡 H1：检索过滤默认关闭

**位置**：`config.py` → `enable_retrieval_filter = False`（standard 模式默认）

**问题**：默认模式下检索阶段无任何过滤。已入库但未被审查发现的毒化文档会被检索并用于生成。

**建议**：即使内容过滤器性能有限，也应默认开启作为兜底防线。

### 🟡 H2：相似度阈值过滤被注释掉

**位置**：`rag/retriever.py` → `retrieve()` 中 `score_threshold` 检查被注释

**问题**：所有检索到的文档无论相似度多低都会进入上下文，降低回答质量且增加攻击面。

**建议**：恢复阈值过滤或提供配置开关。

### 🟡 H3：LLM 输出解析脆弱

**位置**：`resecurity/document_reviewer.py` → `_parse_batch_response()`

**问题**：使用简单正则 `\{[\s\S]*\}` 提取 JSON。若 LLM 输出包含 Markdown 代码块或多个 JSON 对象，可能解析错误或提取到错误内容。

**建议**：使用 `json_repair` 库或更稳健的 JSON 提取策略。

### 🟡 H4：校验器一致性检查基于嵌入相似度

**位置**：`security/validator.py` → `_check_consistency()`

**问题**：通过计算响应与源文档的余弦相似度判断"一致性"。若源文档本身被投毒，生成的有害响应反而会被判定为"一致"。

**建议**：
- 增加独立的事实核查（如调用外部知识源）
- 或至少标记"仅基于 N 个文档的一致性，可信度有限"

### 🟡 H5：无 Prompt Injection 防护

**位置**：多处

**问题**：
- `DocumentReviewer` 将用户文档内容直接拼入 LLM prompt
- `Generator` 将对话历史直接传入消息列表
- 无任何输入清洗或 prompt 分隔机制

**建议**：使用 `<document>` 等 XML 标签包裹外部内容，并在系统提示中明确告知 LLM 忽略内容中的指令。

### 🟡 H6：审核队列无文件锁

**位置**：`resecurity/review_queue_manager.py`

**问题**：JSON 队列文件在多写者场景下可能损坏。

**建议**：使用 `filelock` 库或迁移到 SQLite。

### 🟡 H7：Levenshtein 距离检查仅限同长度

**位置**：`resecurity/rule_checker.py` → `_is_suspicious_package()`

**问题**：`requests` → `requets`（少一个字符）无法被检测，因为长度不同跳过了编辑距离比较。

**建议**：扩大编辑距离检查范围至 ±2 长度差异。

## 四、中/低风险问题（后续优化）

### 🟢 M1：重复的余弦相似度实现

`ContentFilter` 和 `ResponseValidator` 各自实现了一份 `_cosine_similarity()`。

**建议**：提取为共享工具函数。

### 🟢 M2：配置对象中直接存储 API 密钥

`Config` dataclass 直接持有明文 API key，可能通过日志、repr 等泄露。

**建议**：使用 `SecretStr` 类型，并在 `__repr__` 中遮蔽。

### 🟢 M3：测试覆盖率不足

缺少以下模块的单元测试：
- `ContentFilter` 各检测方法
- `ResponseValidator` 各校验规则
- `RuleChecker` 规则匹配
- `ReviewQueueManager` 队列管理
- `TextSplitter` 文本分割

### 🟢 M4：`filtered_content` 字段从未赋值

`FilterResult` 定义了 `filtered_content` 但 `ContentFilter` 从未填充该字段。

### 🟢 M5：无速率限制

无请求频率限制，攻击者可大量查询探测检测边界。

### 🟢 M6：向量库存储无加密

所有文档和元数据以明文存储在 `data/chroma/`。

### 🟢 M7：`stream()` 的 `warnings` 可能包含重复

`validate_node` 将检索阶段的 warnings 与校验阶段的 warnings 合并，但未去重。

### 🟢 M8：`RetrievalResult.is_safe` 语义模糊

当 `content_filter=None` 时，`filtered_count=0` 导致 `is_safe=True`，但实际可能是"未检查"而非"安全"。

## 七、结论

PoisonedRAG 的**三阶段纵深防御架构设计合理**，是当前最大的优势。LLM 批量审查和规则引擎预筛的组合策略高效且实用。测试语料丰富，拦截率达到 100%（在测试条件下）。

**但存在 5 个严重安全隐患**，其中最关键的是**生成校验不拦截响应**和**流式输出绕过校验**——这意味着在实际使用场景中，防护可能不如测试数据显示的那样可靠。

**建议优先修复 S1-S5**，然后再考虑生产部署。修复后系统可达到更高的安全水位。
